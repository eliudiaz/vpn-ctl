# 🚀 PROMPT PARA CLAUDE CODE - Conectar EKS al Transit Gateway sin NAT

```
Genera un script Python usando Pulumi que conecte una VPC de Amazon EKS existente al Transit Gateway de forma ECONÓMICA, eliminando la necesidad de NAT Gateway.

CONTEXTO DEL PROYECTO
─────────────────────────────────────────────────────────────────────────────

Tengo:
1. Un cluster EKS existente en su propia VPC
2. Transit Gateway con VPN Site-to-Site conectado a Vimenca (Checkpoint)
3. Necesito que pods de EKS puedan comunicarse con:
   - Red de Vimenca (172.16.70.0/24) vía Transit Gateway
   - Red de Affinity en otras VPCs (172.33.6.0/28, 172.33.16.0/28)
   - Servicios de AWS (ECR, S3, EC2 API, etc.)

Restricciones:
- ❌ NO usar NAT Gateway (caro: $32/mes + $0.045/GB)
- ✅ Usar VPC Endpoints (económico)
- ✅ Todo tráfico debe ser privado (sin Internet Gateway)
- ✅ Minimizar costos de transferencia de datos

COSTOS COMPARADOS
─────────────────────────────────────────────────────────────────────────────

SOLUCIÓN CON NAT GATEWAY (❌ CARA):
  NAT Gateway:           $32/mes (fixed) x 3 AZs = $96/mes
  Data Processing:       $0.045/GB
  Egress a Internet:     $0.09/GB
  TOTAL ESTIMADO:        $150-300/mes

SOLUCIÓN CON TRANSIT GATEWAY + VPC ENDPOINTS (✅ ECONÓMICA):
  TGW Attachment:        $36/mes
  VPC Endpoints (Interface): $7.20/mes por endpoint x 6 = $43/mes
  VPC Endpoints (Gateway): $0 (S3, DynamoDB)
  Data Processing TGW:   $0.02/GB (más barato que NAT)
  TOTAL ESTIMADO:        $79-120/mes
  
AHORRO: ~$50-180/mes (40-60% menos)

ESPECIFICACIONES TÉCNICAS
─────────────────────────────────────────────────────────────────────────────

1. INPUT PARAMETERS:
   - eks_cluster_name: string (nombre del cluster EKS existente)
   - eks_vpc_id: string (ID de la VPC del EKS)
   - transit_gateway_id: string (TGW existente)
   - region: string (us-east-1, us-west-2, etc.)
   - vimenca_cidr: string (172.16.70.0/24)
   - affinity_cidrs: list[string] (172.33.6.0/28, 172.33.16.0/28)

2. OBTENER INFORMACIÓN DEL CLUSTER EKS:
   - Usar boto3 para obtener:
     * VPC ID del cluster
     * Subnet IDs de los nodos
     * Security Groups
     * Availability Zones usadas

3. TRANSIT GATEWAY ATTACHMENT:
   - Crear attachment usando las subnets privadas de EKS
   - Habilitar DNS support
   - Habilitar propagation de rutas

4. VPC ENDPOINTS (INTERFACE) - CRÍTICO PARA ELIMINAR NAT:
   
   Endpoints requeridos para EKS:
   a) ECR (Docker Registry):
      - com.amazonaws.{region}.ecr.dkr  
      - com.amazonaws.{region}.ecr.api  
   
   b) EC2 (API calls):
      - com.amazonaws.{region}.ec2
   
   c) STS (IAM roles para pods):
      - com.amazonaws.{region}.sts
   
   d) CloudWatch Logs:
      - com.amazonaws.{region}.logs
   
   e) Elastic Load Balancing:
      - com.amazonaws.{region}.elasticloadbalancing
   
   f) Autoscaling (si usas cluster autoscaler):
      - com.amazonaws.{region}.autoscaling
   
   Configuración de cada endpoint:
   - Type: Interface
   - Subnets: Todas las subnets privadas de EKS
   - Security Group: Permitir 443 desde VPC CIDR
   - Private DNS: HABILITADO (crítico)
   - Cost: $0.01/hora = $7.20/mes por endpoint

5. VPC ENDPOINTS (GATEWAY) - GRATIS:
   
   a) S3 (para pull de imágenes, logs, etc.):
      - com.amazonaws.{region}.s3
      - Type: Gateway
      - Route Tables: Todas las route tables privadas
      - Cost: $0 (GRATIS)
   
   b) DynamoDB (si lo usas):
      - com.amazonaws.{region}.dynamodb
      - Type: Gateway
      - Cost: $0 (GRATIS)

6. ROUTE TABLES:
   
   Para cada subnet privada de EKS:
   - Ruta a Vimenca: 172.16.70.0/24 → Transit Gateway
   - Ruta a Affinity: 172.33.0.0/16 → Transit Gateway (ruta agregada)
   - Rutas a servicios AWS: vía VPC Endpoints (automático)
   
   NO agregar ruta default (0.0.0.0/0) - no hay NAT ni IGW

7. SECURITY GROUPS:
   
   a) Security Group para VPC Endpoints:
      - Name: eks-vpc-endpoints-sg
      - Ingress: 
        * Port 443 from VPC CIDR (10.0.0.0/16)
      - Egress: All traffic
   
   b) Actualizar Security Group de Nodes EKS:
      - Agregar egress a VPC Endpoints SG port 443
      - Agregar egress a Vimenca CIDR (172.16.70.0/24)
      - Agregar egress a Affinity CIDR (172.33.0.0/16)

8. DNS RESOLUTION:
   
   VPC Settings:
   - enableDnsHostnames: true
   - enableDnsSupport: true
   - Crítico para que Private DNS de endpoints funcione

9. VALIDACIÓN AUTOMÁTICA:
   
   El script debe incluir función de validación que:
   a) Verifica que attachment está "available"
   b) Verifica que endpoints están "available"
   c) Verifica que rutas se propagaron correctamente
   d) Opcional: Lanza pod de test que intenta:
      - Pull imagen de ECR
      - Acceso a S3
      - Conectividad a Vimenca (ping)

CONSIDERACIONES IMPORTANTES
─────────────────────────────────────────────────────────────────────────────

1. PRIVATE DNS HABILITADO:
   - En VPC Endpoints Interface, SIEMPRE habilitar Private DNS
   - Sin esto, los pods no pueden resolver servicios AWS

2. SECURITY GROUPS:
   - VPC Endpoints necesitan SG que permita 443 desde VPC
   - Nodes necesitan egress a VPC Endpoints

3. SUBNETS:
   - VPC Endpoints deben estar en TODAS las subnets de nodos
   - TGW attachment puede usar un subset de subnets

4. PODS SIN ACCESO A INTERNET:
   - Esto es INTENCIONAL y seguro
   - Todo lo que necesitan está en VPC Endpoints o TGW
   - Si necesitan internet público, usar Internet Gateway (diferente de NAT)

5. ECR PULL:
   - Requiere AMBOS endpoints: ecr.dkr Y ecr.api
   - Sin estos, los pods no pueden pull imágenes

6. IAM ROLES:
   - IRSA (IAM Roles for Service Accounts) requiere endpoint STS
   - Sin STS endpoint, los pods no pueden asumir roles
```
