🎯 Overview

This guide provides step-by-step instructions for configuring a Cisco ASA (Adaptive Security Appliance) to establish a secure, redundant VPN tunnel connection to Affinity’s AWS Transit Gateway infrastructure.

What You’re Building

Your Network              Affinity Transit Gateway      AWS Network
(172.16.0.0/16)          (Hub & Spoke)                 (VPCs)
      │                         │                           │
      ├─ Tunnel 1 (Primary)────►│                           │
      │  (52.14.x.x:500)        ├─ Route Propagation ─────►│
      │                         │                           │
      ├─ Tunnel 2 (Secondary)──►│                           │
      │  (52.14.y.y:500)        │                           │
      │                         │                           │
      └─ BGP 65000             └─ BGP 64512 (AWS)          │
         (Dynamic Routing)       (Dynamic Routing)         │

Key Benefits

  • ✅ Redundancy: Dual tunnels with automatic failover
  • ✅ Dynamic Routing: BGP learns routes automatically
  • ✅ Encryption: IKEv2 with AES-256, SHA2-256
  • ✅ Low Latency: Direct AWS connectivity
  • ✅ AWS Managed: Transit Gateway handles complexity

Estimated Setup Time: 30-45 minutes

🔐 Tunnel Parameters

Encryption & Authentication Standards

All Cisco ASA configurations use these identical parameters:

Parameter Value
IKE Version IKEv2
Phase 1 Encryption AES-256
Phase 1 Integrity SHA2-256
Phase 1 DH Group DH Group 14 (modp4096)
Phase 1 Lifetime 28800 seconds (8 hours)
Phase 2 Encryption AES-256
Phase 2 Integrity SHA2-256
Phase 2 PFS Yes (Recommended)
Phase 2 Lifetime 3600 seconds (1 hour)
Dead Peer Detection (DPD) Enabled
DPD Timeout 10 seconds
DPD Action restart

Why These Settings?

  • IKEv2: Modern, more resilient than IKEv1
  • AES-256: FIPS 140-2 approved, strong encryption
  • SHA2-256: Industry standard integrity checking
  • DH Group 14: Balances security and performance
  • DPD: Detects and recovers from tunnel failures automatically

🔧 Step-by-Step Configuration

STEP 1: Access Cisco ASA

Via ASDM (Web GUI): 1. Open ASDM application or navigate to https://[asa-ip]:8443 2. Log in with admin credentials 3. Navigate to Configuration → Site-to-Site VPN → IPSec

Via CLI (SSH):

ssh admin@[asa-ip]
# Or
telnet [asa-ip]

STEP 2: Create IKE Policy (Phase 1)

Via ASDM: 1. Navigate to Configuration → Site-to-Site VPN → IKE 2. Click Add to create new policy 3. Configure: - Priority: 1 - IKE Version: IKEv2 - Encryption: AES-256 - Integrity: SHA-256 - DH Group: 14 - Lifetime (seconds): 28800

  1. Click OK

Via CLI:

configure terminal
crypto ikev2 policy 1
  encryption aes-256
  integrity sha256
  group 14
  lifetime 28800
exit

STEP 3: Create IPSec Transform Set (Phase 2)

Via ASDM: 1. Navigate to Configuration → Site-to-Site VPN → IPSec 2. Click Transform Sets → Add 3. Configure: - Name: ATG-Transform-Set-1 - Encryption: AES-256 - Integrity (Authentication): SHA-256 - Enable PFS: Yes - DH Group: 14 - Mode: Tunnel - Lifetime (seconds): 3600

  1. Click OK

Via CLI:

crypto ipsec transform-set ATG-Transform-Set-1 esp-aes 256 esp-sha-256
  mode tunnel
  pfs group14

STEP 4: Create Crypto ACL (Traffic Selectors)

Via ASDM: 1. Navigate to Configuration → Objects → Access Lists 2. Click Add to create new ACL 3. Configure: - Name: VPN-to-Affinity-ACL - Access List Type: Extended - Add rule: Permit IP from 172.16.0.0 255.255.0.0 to 10.0.0.0 255.255.0.0

  1. Click OK

Via CLI:

access-list VPN-to-Affinity-ACL extended permit ip 172.16.0.0 255.255.0.0 10.0.0.0 255.255.0.0

STEP 5: Configure IPSec Connection (Tunnel 1)

Via ASDM: 1. Navigate to Configuration → Site-to-Site VPN → IPSec Connections 2. Click Add to create connection 3. Configure General: - Connection Name: Affinity-ATG-Tunnel-1 - Connection Type: Site to Site - Interface: Outside (external interface) - Peer IP Address: 52.14.X.X (Affinity endpoint) - Authentication Type: Pre-shared Key - Pre-shared Key: [PSK provided by Affinity] (case-sensitive!)

  1. Configure IPSec:

    • IKE Policy: Select policy created in Step 2
    • Transform Set: Select ATG-Transform-Set-1
    • Access List: Select VPN-to-Affinity-ACL
    • PFS Group: 14

  2. Click OK

  3. Repeat for Tunnel 2:

    • Name: Affinity-ATG-Tunnel-2
    • Peer IP: 52.14.Y.Y
    • PSK: [Second PSK from Affinity]

Via CLI:

crypto map ATG-Map 1 match address VPN-to-Affinity-ACL
crypto map ATG-Map 1 set peer 52.14.X.X
crypto map ATG-Map 1 set ikev2 ike-policy 1
crypto map ATG-Map 1 set transform-set ATG-Transform-Set-1
crypto map ATG-Map 1 set pfs group14
crypto map ATG-Map 1 set lifetime seconds 3600

crypto map ATG-Map interface outside

STEP 6: Configure Tunnel Interfaces

Via CLI (Creating Logical Interfaces):

interface Tunnel1
  ip address 169.254.X.2 255.255.255.252
  tunnel source [your-public-ip]
  tunnel destination 52.14.X.X
  tunnel mode ipsec ipv4
  tunnel protection ipsec profile ATG-Tunnel-1
exit

interface Tunnel2
  ip address 169.254.Y.2 255.255.255.252
  tunnel source [your-public-ip]
  tunnel destination 52.14.Y.Y
  tunnel mode ipsec ipv4
  tunnel protection ipsec profile ATG-Tunnel-2
exit

STEP 7: Create ACL for VPN Traffic

Via ASDM: 1. Navigate to Configuration → Objects → Access Lists 2. Create new ACL for device: - Name: VPN-Policy-ACL - Add rule: Permit traffic between your network and Affinity

Via CLI:

access-list VPN-Policy-ACL extended permit ip 172.16.0.0 255.255.0.0 10.0.0.0 255.255.0.0

STEP 8: Create Network Address Translation (NAT) Exemption

Important: VPN traffic must NOT be NAT’d

Via CLI:

# Exempt VPN traffic from NAT
access-list NoNAT extended permit ip 172.16.0.0 255.255.0.0 10.0.0.0 255.255.0.0
nat (inside,outside) source static 172.16.0.0 172.16.0.0 destination static 10.0.0.0 10.0.0.0 no-proxy-arp

STEP 9: Save Configuration

Via ASDM: 1. Click File → Save 2. Wait for configuration to save

Via CLI:

write memory
# or
copy running-config startup-config

🔄 BGP Dynamic Routing

Step 1: Enable BGP

Via CLI:

router bgp 65000
  bgp log-neighbor-changes
  neighbor 169.254.X.1 remote-as 64512
  neighbor 169.254.Y.1 remote-as 64512
  !
  address-family ipv4
    neighbor 169.254.X.1 activate
    neighbor 169.254.Y.1 activate
    network 172.16.0.0 mask 255.255.0.0
  exit-address-family
exit

Step 2: Configure BGP Timers (Optional)

router bgp 65000
  neighbor 169.254.X.1 timers 60 180
  neighbor 169.254.Y.1 timers 60 180
exit

Step 3: Redistribute Connected Routes (Optional)

router bgp 65000
  address-family ipv4
    redistribute connected
  exit-address-family
exit

Step 4: Verify BGP Configuration

show bgp summary
show bgp neighbors
show ip bgp

From Cisco ASA:

From Affinity Side:

🐛 Troubleshooting

Issue: Tunnel Stays DOWN

Symptoms: Tunnels show DOWN or “not enabled”

Diagnosis:

show crypto ipsec sa brief

show crypto ikev2 sa brief

show crypto engine connections active

Solutions:

  1. Verify PSK Match:
    • Check PSK in ASA matches exactly what Affinity provided
    • PSKs are case-sensitive
    • No extra spaces or characters
    show crypto map
  2. Check ACL Match:
    • Verify crypto ACL permits traffic between networks
    • Traffic must match exactly
    show access-list VPN-to-Affinity-ACL
  3. Verify Encryption Settings:
    • Confirm IKEv2, AES-256, SHA2-256 selected
    • Check DH Group 14 enabled
    show crypto ike policy
show crypto ipsec transform-set
  4. Check Interface:
    • Verify external interface enabled and has route to peer
    show interface outside
show route | include 52.14

Issue: BGP Routes Not Learning

Symptoms: Tunnel UP but no routes appearing

Diagnosis:

show bgp summary
# Check if peers show "Up"

show bgp neighbors 169.254.X.1
# Detailed peer information

show ip bgp
# Should show routes from AWS

Solutions:

  1. Verify BGP Enabled:
    • Confirm BGP enabled and AS number correct
    show run router bgp
  2. Check Neighbor Configuration:
    • Verify neighbor IP matches tunnel inside IP
    • Confirm remote AS = 64512
    show bgp neighbors
  3. Review BGP Timers:
    • Keep alive should be ≤ 60 seconds
    • Hold time should be ≥ 180 seconds
    show bgp timers

Issue: Traffic Not Passing

Symptoms: Tunnel UP, routes learned, but no data flow

Diagnosis:

# Check if traffic matches crypto ACL
show access-list VPN-to-Affinity-ACL

# Monitor tunnel traffic
debug crypto ipsec

# Check NAT exemption
show nat detail

Solutions:

  1. Verify ACL Configuration:
    • Confirm ACL permits traffic source → destination
    • Traffic selectors must match exactly
    • No overlapping or conflicting rules
  2. Check NAT Exemption:
    • Ensure VPN traffic exempted from NAT
    • Source/destination must NOT be translated
  3. Enable Debug (Temporary):
    • Monitor tunnel activity
    debug crypto ipsec
debug crypto ikev2
# Disable with: undebug all

🧪 Joint E2E Testing (Phases 3-7)

After device configuration is complete, both Affinity and your DevOps team conduct structured testing via the master protocol: VPN_E2E_TESTING_PROTOCOL.md

This section covers Cisco ASA-specific testing procedures for each phase.

Phase 3: IKE/IPSec Tunnel Establishment (Layer 1-2)

Timeline: Immediately after configuration is saved and enabled

What happens: Your device initiates IKE; AWS responds; tunnels reach UP state

Your action: Monitor tunnel negotiation

# Real-time tunnel status
show crypto ikev2 sa

# Expected output (after successful negotiation):
# IKEv2 SAs:
# Session-id:0x0, IKE_SA type:IPsecClient Established 1-time SA
# Peer IP:52.14.123.45:500
# COMPLETE [ JH ] [ SA ]

# Check IPSec security associations
show crypto ipsec sa

# Expected output:
# interface: outside
#  Crypto map tag: AWS_TUNNEL_1, seq num: 10
#   Peer address(es): 52.14.123.45
#   Protected data flows:
#    permit ip any any
#   PFS (Y/N): Y
#   Transform sets in use:
#    AWS_TRANSFORM_SET
#  Connections:
#   Active SA count: 2 (inbound and outbound)

# Monitor in real-time
debug crypto ikev2
# [Wait a few seconds, observe IKE negotiation]
undebug all

Affinity verifies: AWS console shows both tunnels UP (via skill-vpn-connectivity)

Gate 3.1: Both tunnels show active SAs on both sides

If tunnels stay DOWN after 30 seconds: See Troubleshooting → “Tunnel Stays DOWN”

Phase 4: BGP Route Exchange (Layer 3)

Timeline: 5-15 seconds after tunnels reach UP

What happens: BGP neighbors establish; routes learned automatically

Your action: Monitor BGP neighbor state

# Check BGP summary
show bgp summary

# Expected output:
# Neighbor        V    AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down State/PfxRcd
# 169.254.10.1    4 64512     10      10        5    0    0 00:05:10        3
# 169.254.11.1    4 64512     10      10        5    0    0 00:05:10        3

# View routes received from BGP
show bgp ipv4 unicast neighbors 169.254.10.1 received-routes

# View routes in BGP table
show bgp ipv4 unicast summary

# View routes in main routing table (should include BGP routes)
show route bgp

Affinity verifies: AWS Transit Gateway route table contains your CIDRs with state=active

Gate 4.1: BGP neighbors show in Established state; routes appear in both TGW table and your routing table

If routes don’t appear: See Remediation Playbooks → “BGP Routes Not Appearing”

Phase 5: Data Plane Traffic Test (Layer 4)

Timeline: After Phase 4 gate passes

What happens: Test actual traffic flow across tunnel

Affinity’s Test (from EKS pod)

# Affinity pings a host on your network
kubectl run vpn-test --rm -it --image=alpine -- sh

# Inside pod:
ping -c 10 [YOUR_TEST_IP]  # e.g., 172.16.1.100
# Expected: 0% packet loss, round-trip time ~45-100ms

# Test MTU
ping -c 3 -M do -s 1400 [YOUR_TEST_IP]  # May fail
ping -c 3 -M do -s 1350 [YOUR_TEST_IP]  # Should succeed

Your Confirmation

On your test host, monitor traffic arrival:

# Monitor incoming traffic from Affinity
show debug
debug ip icmp                    # Log ICMP traffic
debug ip packet detail           # Log all packets
# [Trigger ping from Affinity]
undebug all

# Verify tunnel is carrying traffic
show crypto ipsec sa detail | grep bytes

# Check BGP routes are in routing table
show route bgp | include 10.0

# View security logs
show log

Gate 5.1: Bidirectional ping succeeds with ≤1% loss; MTU 1350+ working

If traffic doesn’t pass: See Remediation Playbooks → “Traffic Not Passing”

Phase 6: Redundancy & Failover Test (Layer 5) — OPTIONAL

Timeline: Can be deferred to maintenance window

What happens: One tunnel is disabled; verify other handles all traffic

Your action: Continuous ping during test

# Start extended ping to Affinity test IP
ping [AFFINITY_TEST_IP] repeat 1000

# Affinity will disable Tunnel 1 on their side
# Expected ping behavior:
# [Normal] ~1ms latency, 0% loss
# [Tunnel 1 DOWN] Brief interruption (1-3 sec)
# [DPD timeout] 10 second delay (Cisco default)
# [BGP reconvergence] Another 5-10 seconds
# [Resumed] Ping continues normally through Tunnel 2

# Total disruption: 15-25 seconds

# Monitor tunnel status during failover
show crypto ipsec sa summary
# Should show Tunnel 2 active, Tunnel 1 inactive

Gate 6.1: Single tunnel failure does not cause total outage

Phase 7: Operational Sign-Off

Timeline: After all Phase 5 (or Phase 6) gates pass

Action: Complete bilateral sign-off checklist in VPN_E2E_TESTING_PROTOCOL.md Phase 7 section

Cisco ASA Verification Checklist: - [ ] show crypto ikev2 sa shows both IKE SAs ESTABLISHED - [ ] show crypto ipsec sa shows active SAs for both tunnels - [ ] show bgp summary shows neighbors in Established state - [ ] show bgp ipv4 unicast summary shows received routes - [ ] Data plane ping succeeds (0% loss) - [ ] Failover test completed (if performed) - [ ] Configuration backed up and documented

Once signed: Tunnel is production-ready

📋 Configuration Checklist

Before declaring configuration complete:

IKE Configuration: - [ ] IKE policy created with IKEv2, AES-256, SHA2-256, Group 14 - [ ] IKE lifetime set to 28800 seconds (8 hours)

IPSec Configuration: - [ ] Transform set created with AES-256, SHA2-256, Group 14 - [ ] Transform set lifetime set to 3600 seconds (1 hour) - [ ] PFS enabled with Group 14 - [ ] PSKs entered for both tunnels (case-sensitive)

Crypto Map: - [ ] Crypto ACL permits traffic between local and remote CIDR blocks - [ ] Crypto map configured for both tunnels - [ ] Crypto map applied to external interface

NAT Configuration: - [ ] NAT exemption configured for VPN traffic - [ ] VPN traffic specifically excluded from translation

BGP Configuration (if using): - [ ] BGP enabled with correct local AS number - [ ] Neighbors configured with correct IP and remote AS - [ ] Network statements include local CIDR blocks

Verification: - [ ] Both tunnels show UP - [ ] BGP peers show as “Up” (if using BGP) - [ ] Routes to AWS appearing in routing table - [ ] Ping test to AWS network successful
