🎯 Overview

This guide provides step-by-step instructions for configuring a Checkpoint R80.10+ firewall to establish a secure, redundant VPN tunnel connection to Affinity’s AWS Transit Gateway infrastructure.

What You’re Building

Your Network              Affinity Transit Gateway      AWS Network
(172.16.0.0/16)          (Hub & Spoke)                 (VPCs)
      │                         │                           │
      ├─ Tunnel 1 (Primary)────►│                           │
      │  (52.14.x.x:500)        ├─ Route Propagation ─────►│
      │                         │                           │
      ├─ Tunnel 2 (Secondary)──►│                           │
      │  (52.14.y.y:500)        │                           │
      │                         │                           │
      └─ BGP 65000             └─ BGP 64512 (AWS)          │
         (Dynamic Routing)       (Dynamic Routing)         │

Key Benefits

  • ✅ Redundancy: Dual tunnels with automatic failover
  • ✅ Dynamic Routing: BGP learns routes automatically
  • ✅ Encryption: IKEv2 with AES-256, SHA2-256
  • ✅ Low Latency: Direct AWS connectivity
  • ✅ AWS Managed: Transit Gateway handles complexity

Estimated Setup Time: 30-45 minutes

🔐 Tunnel Parameters

Encryption & Authentication Standards

All Checkpoint configurations use these identical parameters:

Parameter Value
IKE Version IKEv2
Phase 1 Encryption AES-256
Phase 1 Integrity SHA2-256
Phase 1 DH Group DH Group 14 (modp4096)
Phase 1 Lifetime 28800 seconds (8 hours)
Phase 2 Encryption AES-256
Phase 2 Integrity SHA2-256
Phase 2 PFS Optional (Recommended)
Phase 2 Lifetime 3600 seconds (1 hour)
DPD Timeout 30 seconds
DPD Action restart

Why These Settings?

  • IKEv2: Modern, more resilient than IKEv1
  • AES-256: FIPS 140-2 approved, strong encryption
  • SHA2-256: Industry standard integrity checking
  • DH Group 14: Balances security and performance
  • DPD: Detects and recovers from tunnel failures automatically

🔧 Step-by-Step Configuration

STEP 1: Open SmartDashboard

  1. Launch SmartDashboard
  2. Log in with admin credentials
  3. Navigate to Manage & Settings

STEP 2: Create Customer Gateway Object

  1. In SmartDashboard, go to Objects → New → Interoperable Device
  2. Configure:
    • Name: Affinity-ATG (or your preferred name)
    • IPv4 Address: [Your public IP]
    • Type: VPN Gateway
  3. Click Create

STEP 3: Create VPN Community

  1. Go to Manage & Settings → VPN
  2. Click New → Star Community
  3. Configure General:
    • Name: Affinity-ATG-Community
    • Description: Affinity Transit Gateway Connection
  4. Add Gateways:
    • Local Gateway: Your Checkpoint firewall
    • Remote Gateway: Affinity-ATG (created in Step 2)
  5. Click Next

STEP 4: Configure VPN Tunnel Settings

  1. In Star Community, go to Encryption
  2. Set IPSec Encryption Policy:
    • IKE: IKEv2 only
    • Encryption: AES-256
    • Authentication: SHA2-256
    • DH Group: Group 14
  3. Set IPSec Data Integrity:
    • Authentication: SHA2-256
  4. Set IPSec Data Encryption:
    • Encryption: AES-256
  5. Advanced Settings:
    • DPD Action: Restart
    • DPD Timeout: 30 seconds
    • Lifetime: 28800 seconds (Phase 1), 3600 seconds (Phase 2)

STEP 5: Configure Pre-Shared Keys (PSKs)

  1. In Star Community, go to Secrets
  2. For Tunnel 1:
    • Click Manage Secrets
    • Enter PSK provided by Affinity
    • Click OK
  3. Repeat for Tunnel 2 with second PSK

⚠️ Important: PSKs are case-sensitive. Copy exactly as provided.

STEP 6: Configure Tunnel Inside IPs

  1. Go to VPN Tunnels tab in Star Community
  2. For Tunnel 1:
    • Local IP: 169.254.X.2 (your side)
    • Remote IP: 169.254.X.1 (AWS side)
  3. For Tunnel 2:
    • Local IP: 169.254.Y.2 (your side)
    • Remote IP: 169.254.Y.1 (AWS side)

STEP 7: Configure Network Objects

Create network objects for routes through tunnel:

  1. Go to Objects → Networks
  2. Create object for each CIDR block behind Affinity:
    • Name: Affinity-Network (or specific name)
    • IPv4 Network: 10.0.0.0/16 (example Affinity CIDR)
    • Mask: 255.255.0.0
  3. Create object for your networks (if not already exists):
    • Name: Local-Network
    • IPv4 Network: 172.16.0.0/16 (your network example)
    • Mask: 255.255.0.0

STEP 8: Create VPN Access Rule

  1. Go to Policy → Access Control
  2. Create new rule:
    • Name: VPN-Tunnel-to-Affinity
    • Source: Local-Network (your side)
    • Destination: Affinity-Network (AWS side)
    • Service: Any
    • Action: Accept
    • VPN: Select Affinity-ATG-Community
  3. Log: Enable logging for troubleshooting

STEP 9: Publish & Install Policy

  1. Click Policy → Publish
  2. Review changes
  3. Click Install
  4. Select relevant gateways
  5. Click Install Policy

Wait for installation to complete (typically 2-5 minutes).

🔄 BGP Dynamic Routing

Step 1: Enable BGP on Gateway

  1. Go to Manage & Settings → Network Management
  2. Select your gateway
  3. Go to BGP tab
  4. Enable BGP
  5. Set Local BGP AS: Your assigned ASN (e.g., 65000)

Step 2: Configure BGP Neighbors

For each tunnel, configure BGP peer:

  1. In BGP settings, click Add Neighbor
  2. Configure for Tunnel 1:
    • Neighbor IP: 169.254.X.1 (AWS side)
    • Remote AS: 64512 (AWS ASN)
    • Hold Time: 180 seconds
    • Keep Alive: 60 seconds
  3. Configure for Tunnel 2:
    • Neighbor IP: 169.254.Y.1 (AWS side)
    • Remote AS: 64512
    • Hold Time: 180 seconds
    • Keep Alive: 60 seconds

Step 3: Configure Route Propagation

  1. Go to BGP → Inbound/Outbound Policy
  2. Inbound: Accept all routes from AWS
  3. Outbound: Advertise your CIDR blocks

Step 4: Publish & Install

  1. Publish the changes
  2. Install on your gateway

🐛 Troubleshooting

Issue: Tunnel Stays DOWN

Symptoms: Both tunnels show DOWN in VPN Manager

Diagnosis:

# Check IPSec status
fw stat -sc

# Check if tunnel can reach endpoint
fw fetch 52.14.X.X 500

Solutions:

  1. Verify PSK Match:
    • Check PSK in Checkpoint matches exactly what Affinity provided
    • PSKs are case-sensitive
    • No extra spaces or characters
  2. Check Firewall Rules:
    • Ensure outbound UDP 500, 4500 allowed
    • No DLP/IPS blocking IPSec
  3. Verify Encryption Settings:
    • Confirm IKEv2, AES-256, SHA2-256 selected
    • Check DH Group 14 enabled
  4. Check Interface IP:
    • Verify your firewall’s public IP correct
    • Confirm no NAT masking tunnel traffic

Issue: BGP Routes Not Learning

Symptoms: Tunnel UP but no routes appearing in routing table

Diagnosis:

# Check BGP neighbor status
netstat -rn | grep Affinity

# Check BGP debug logs
fw ctl debug -m cpm +bgp +route

Solutions:

  1. Verify BGP Enabled:
    • Confirm BGP enabled on gateway
    • Check BGP AS number configured
  2. Check Neighbor Configuration:
    • Verify neighbor IP (inside tunnel IP)
    • Confirm AS number 64512 for AWS
  3. Review BGP Timers:
    • Hold time should be ≥ 180 seconds
    • Keep alive should be ≤ 60 seconds

Issue: Traffic Not Passing

Symptoms: Tunnel UP, routes learned, but no data flow

Diagnosis:

# Check access rules
fw stat -c | grep VPN

# Monitor tunnel traffic
fw stat -sc | grep -E "Packet|Byte"

Solutions:

  1. Verify Access Rules:
    • Confirm rule allows traffic source → destination
    • Check VPN community assigned
    • Verify rule is enabled and before deny rules
  2. Check Network Objects:
    • Ensure source/destination IPs in correct objects
    • Verify CIDR ranges are inclusive
  3. Enable Logging:
    • Log all VPN traffic temporarily
    • Review logs for accepted/dropped packets

🧪 Joint E2E Testing (Phases 3-7)

After device configuration is complete, both Affinity and your DevOps team conduct structured testing via the master protocol: VPN_E2E_TESTING_PROTOCOL.md

This section covers Checkpoint-specific testing procedures for each phase.

Phase 3: IKE/IPSec Tunnel Establishment (Layer 1-2)

Timeline: Immediately after configuration is committed

What happens: Your device initiates IKE; AWS responds; tunnels reach UP state

Your action: Monitor tunnel negotiation

# Real-time tunnel status
watch -n 2 'fw stat -sc | grep -E "Tunnel|SA|IKE"'

# Expected progression (in VPN SA list):
# [Initial] No entries
# [After ~2s] IKE SA 1 ESTABLISHED, Phase 2 negotiating
# [After ~5s] IKE SA 1 ESTABLISHED, IPSec SA 1 ACTIVE
# [After ~10s] IKE SA 1 ESTABLISHED, IPSec SA 1 ACTIVE
#              IKE SA 2 ESTABLISHED, IPSec SA 2 ACTIVE

# Detailed tunnel view
vpn tunnel get -x 0
vpn tunnel get -x 1

# Expected: Phase 1 & Phase 2 both show "ESTABLISHED"

Affinity verifies: AWS console shows both tunnels UP (via skill-vpn-connectivity)

Gate 3.1: Both tunnels show UP on both sides

If tunnels stay DOWN after 30 seconds: See Troubleshooting → “Tunnel stays DOWN”

Phase 4: BGP Route Exchange (Layer 3)

Timeline: 5-15 seconds after tunnels reach UP

What happens: BGP neighbors establish; routes learned automatically

Your action: Monitor BGP neighbor state

# Check BGP learned routes
netstat -rn | grep 169.254

# Expected output shows routes to AWS networks via tunnel inside IPs:
# Destination  Gateway           Genmask      Flags Metric Ref Use Iface
# 10.0.0.0/16  169.254.10.1      255.255.0.0  UG    100    0   0   tun...
# 10.1.0.0/16  169.254.10.1      255.255.0.0  UG    100    0   0   tun...

# Detailed BGP neighbor status
fw ctl debug -m cpm +bgp +route
# [Wait 10 seconds, observe BGP updates]
fw ctl debug -off

# View learned BGP routes
show route bgp

Affinity verifies: AWS Transit Gateway route table contains your CIDRs with state=active

Gate 4.1: BGP neighbors Established; routes appear in both TGW table and your device

If routes don’t appear: See Remediation Playbooks → “BGP Routes Not Appearing”

Phase 5: Data Plane Traffic Test (Layer 4)

Timeline: After Phase 4 gate passes

What happens: Test actual traffic flow across tunnel

Affinity’s Test (from EKS pod)

# Affinity pings a host on your network
kubectl run vpn-test --rm -it --image=alpine -- sh

# Inside pod:
ping -c 10 [YOUR_TEST_IP]  # e.g., 172.16.1.100
# Expected: 0% packet loss, round-trip time ~45-100ms

# Test MTU (see your network team for test IP)
ping -c 3 -M do -s 1400 [YOUR_TEST_IP]  # May fail
ping -c 3 -M do -s 1350 [YOUR_TEST_IP]  # Should succeed

Your Confirmation

On your test host, monitor traffic arrival:

# Monitor incoming traffic from Affinity
tcpdump -i any "src 10.0.0.0/8"

# Expected: ICMP echo-request packets arriving from Affinity CIDR
# Verify: Source IP is from Affinity network (not NATed)
# Confirm: Traffic is arriving (ICMP echo request visible)

# Verify return path uses tunnel
netstat -rn | grep 10.0

# Expected: Routes to 10.0.0.0/8 show tunnel device as gateway

Gate 5.1: Bidirectional ping succeeds with ≤1% loss; MTU 1350+ working

If traffic doesn’t pass: See Remediation Playbooks → “Traffic Not Passing”

Phase 6: Redundancy & Failover Test (Layer 5) — OPTIONAL

Timeline: Can be deferred to maintenance window

What happens: One tunnel is disabled; verify other handles all traffic

Your action: Continuous ping during test

# Start continuous ping to Affinity test IP
ping -i 1 [AFFINITY_TEST_IP] | tee failover-test.log

# Affinity will disable Tunnel 1 on their side
# Expected ping behavior:
# [Normal] ~1ms latency, 0% loss
# [Tunnel 1 DOWN] Brief interruption (1-3 sec) as traffic shifts to Tunnel 2
# [DPD timeout] 10-30 second delay while DPD detects failure
# [BGP reconvergence] Another 5-10 seconds
# [Resumed] Ping continues normally through Tunnel 2

# Total disruption: 15-40 seconds (acceptable for most SLAs)

Gate 6.1: Single tunnel failure does not cause total outage; failover completes in <90 seconds

Phase 7: Operational Sign-Off

Timeline: After all Phase 5 (or Phase 6) gates pass

Action: Complete bilateral sign-off checklist in VPN_E2E_TESTING_PROTOCOL.md Phase 7 section

Checklist includes: - [ ] Both tunnels UP on both sides - [ ] BGP routes exchanged bidirectionally - [ ] Data plane traffic bidirectional (0% loss) - [ ] MTU ≥1350 bytes verified - [ ] Failover tested (if performed) - [ ] Device configuration documented - [ ] Affinity & Peer DevOps sign-off

Once signed: Tunnel is production-ready

📋 Configuration Checklist

VPN Tunnel Setup: - [ ] Interoperable Device created with public IP - [ ] VPN Community created and named - [ ] PSKs entered for both tunnels - [ ] Inside tunnel IPs configured (169.254.x.x/30) - [ ] Encryption: IKEv2, AES-256, SHA2-256 - [ ] DPD enabled (30 seconds, restart action)
