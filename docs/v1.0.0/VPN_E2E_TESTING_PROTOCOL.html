🎯 Protocol Overview

This protocol defines a structured 7-phase handoff process between Affinity DevOps and peer organization DevOps to bring up VPN tunnels from “Pulumi deployed” to “operationally ready.”

Why This Protocol Exists

  1. AWS VPN is responder-only — peer MUST initiate IKE; Affinity cannot verify tunnel readiness alone
  2. No BGP visibility from AWS API — can’t observe neighbor state, only “X BGP ROUTES” in StatusMessage
  3. Two independent teams — need clear handoff checkpoints and joint go/no-go gates
  4. Failure isolation — 5 layers (reachability → IKE → IPSec → BGP → traffic) require systematic testing

Phases at a Glance

Phase Owner Focus Go/No-Go Gate
0 Affinity Pre-deployment checklist Pulumi stack deployed
1 Affinity → Peer Deliver tunnel details securely Peer acknowledges receipt
2 Peer Configure device per guide Peer reports ready
3 Both IKE/IPSec tunnel UP Both tunnels UP on both sides
4 Both BGP routes exchanged Routes in TGW table + peer learned
5 Both Bidirectional traffic Ping succeeds, MTU verified
6 Both (optional) Failover works Both tunnels recover post-failover
7 Both Sign-off documents Bilateral sign-off form completed

Phase 3: Layer 1-2 Tunnel Establishment (IKE/IPSec)

Critical Context: AWS is Responder-Only

AWS Transit Gateway VPN is always in responder mode. The peer device MUST initiate IKE Main Mode or Aggressive Mode. AWS will respond with tunnel negotiation.

This means: 1. Peer initiates: Device sends IKE_SA_INIT to AWS tunnel endpoint 2. AWS responds: Completes IKE negotiation 3. IPSec SAs established: Both tunnels come UP 4. Timely: Should take 5-30 seconds from peer initiation

Timeline & Responsibilities

Step Owner Action Expected Time
1 Peer Initiate IKE from device (enable tunnel/VPN) T+0s
2 AWS/TGW Respond to IKE; negotiate Phase 2 T+2-5s
3 Affinity Monitor tunnel state with watch command T+0s continuously
4 Both Verify both tunnels reach UP state T+2-10s

Phase 4: Layer 3 BGP Route Exchange

How BGP Works with AWS VPN

  1. BGP Neighbors: Peer and AWS establish BGP session over tunnel inside IP (169.254.x.1)
  2. Peer AS number: Peer’s assigned ASN (e.g., 65000 for Vimenca)
  3. AWS AS number: 64512 (constant for all VPN peers)
  4. Route Learning: BGP advertises CIDRs automatically
  5. Affinity visibility: AWS API returns “X BGP ROUTES” in StatusMessage but NOT actual neighbor state

Timeline & Responsibilities

Step Owner Action Expected Time
1 Peer BGP neighbors already configured (from Phase 2) N/A
2 AWS/TGW Receives tunnel UP; initiates BGP T+0-5s post-tunnel UP
3 Peer Responds to BGP neighbor; exchanges routes T+5-10s
4 Affinity Verifies peer CIDRs in TGW route table T+10-15s

Phase 5: Layer 4 Data Plane Traffic Test

Purpose

Verify actual traffic can flow bidirectionally across the tunnel, confirming: 1. Network routing is correct 2. MTU is sufficient for encrypted traffic 3. Return traffic is using tunnel (not alternate path)

Prerequisite: Coordinate Test Hosts

Before testing, identify test endpoints:

Affinity side: - EKS pod or EC2 instance in VPC with private IP (e.g., 10.0.1.100) - Must be in a subnet with route pointing to TGW for peer CIDR

Peer side: - Any host in peer’s network segment (e.g., 172.16.1.100) - Must reach the tunnel device for routing

Affinity Test: Ping from EKS Pod

#!/bin/bash
PEER_TEST_IP="172.16.1.100"  # Host on peer network
POD_NAMESPACE="default"
POD_NAME="vpn-test-$(date +%s)"

# Create temporary test pod
kubectl run "$POD_NAME" \
  --rm -it \
  --image=alpine \
  --restart=Never \
  --namespace="$POD_NAMESPACE" \
  -- sh -c "
    echo 'Testing tunnel reachability...'

    # Test 1: ICMP ping
    echo 'Test 1: ICMP Ping'
    ping -c 10 $PEER_TEST_IP

    # Test 2: TCP connectivity
    echo 'Test 2: TCP Connectivity (port 22 example)'
    nc -vz -w 5 $PEER_TEST_IP 22

    # Test 3: Traceroute to verify path
    echo 'Test 3: Traceroute'
    traceroute $PEER_TEST_IP

    # Test 4: MTU test (see MTU Test section)
    echo 'Test 4: MTU Test - 1400 bytes'
    ping -c 3 -M do -s 1400 $PEER_TEST_IP && echo 'MTU 1400: OK' || echo 'MTU 1400: FAILED'

    echo 'Test 5: MTU Test - 1350 bytes'
    ping -c 3 -M do -s 1350 $PEER_TEST_IP && echo 'MTU 1350: OK' || echo 'MTU 1350: FAILED'
"

Expected Output:

ICMP ping test:
  PING 172.16.1.100 (172.16.1.100) 56(84) bytes of data.
  64 bytes from 172.16.1.100: icmp_seq=1 ttl=63 time=45.2 ms
  [9 more packets]
  --- 172.16.1.100 statistics ---
  10 packets transmitted, 10 received, 0% packet loss

TCP connectivity: Connection successful
Traceroute: Final hop is the peer gateway

MTU tests:
  MTU 1400: OK (or FAILED - see below)
  MTU 1350: OK

MTU Test Details

IPSec adds ~50-70 bytes of header overhead (IKEv2 + ESP header + padding). AWS recommends maximum payload of 1394 bytes.

Test Sequence:

  1. Test 1400 bytes: Likely to fail (ICMP + IPSec > 1500 Ethernet MTU)
  2. Test 1350 bytes: Should succeed (standard safe limit)
  3. If 1350 fails: Check peer MTU configuration, may need to lower DF (Don’t Fragment) bit handling

Peer-Side Confirmation:

Peer team confirms traffic arriving:

# On peer network host:
tcpdump -i eth0 -n "src 10.0.1.100 and dst 172.16.1.100"

# Expected: ICMP echo requests arriving with source IP from Affinity

# Important: Verify traffic arrives from tunnel, not internet:
netstat -rn | grep 10.0.1.0/24
# Should show route via tunnel device/inside IP

Phase 6: Layer 5 Redundancy & Failover Testing

When to Perform This Phase

Required for: Production sign-off (mandatory before go-live) Optional for: Initial testing (can schedule for future maintenance window)

If deferring: Document in sign-off sheet “Failover test: Scheduled for [date/maintenance window]”

Failover Mechanism

AWS VPN uses dual active tunnels (not active-standby). When one tunnel fails: 1. Detection: DPD timeout triggers (10-30 seconds per device) 2. BGP reconvergence: Neighbor goes down; routes via remaining tunnel 3. Traffic impact: ~30-90 second disruption (acceptable for most applications)

Failover Test Procedure

Step 1: Establish Baseline

# From Affinity:
watch -n 2 'aws ec2 describe-vpn-connections \
  --filters "Name=tag:Name,Values=$PEER_NAME" \
  --region us-east-2 \
  --query "VpnConnections[0].VgwTelemetry[*].[OutsideIpAddress,Status.TunnelStatus]" \
  --output table'

# From Peer (continuous ping):
ping -i 1 <AFFINITY_TEST_IP> | tee failover-test.log

# Expected: Both tunnels UP, ping continuous 0% loss

Step 2: Disable Tunnel 1 on Affinity

# Affinity uses AWS console or CLI to disable Tunnel 1:
# Option A (CLI - Not available via standard describe-vpn-connections)
# Option B (Console): EC2 → VPN Connections → Select connection → Modify → Disable Tunnel 1

# For testing via script, create custom monitoring:
aws ec2 describe-vpn-connections \
  --filters "Name=tag:Name,Values=$PEER_NAME" \
  --region us-east-2 \
  --query 'VpnConnections[0].VgwTelemetry[0].Status.TunnelStatus' \
  --output text
# Expected to show: DOWN (once disabled)

Step 3: Observe Failover from Both Sides

Affinity observations: - Tunnel 1 transitions to DOWN (immediate) - Tunnel 2 remains UP (continuous traffic) - Possible brief BGP route recalculation (5-30 seconds)

Peer observations: - Continuous ping shows brief gap (may see 1-3 packet loss) - After DPD timeout + BGP reconvergence, ping resumes normal

Step 4: Re-Enable Tunnel 1 and Verify Recovery

# Affinity: Re-enable Tunnel 1 in console/via modification
# Monitor as before:
watch -n 2 'aws ec2 describe-vpn-connections \
  --filters "Name=tag:Name,Values=$PEER_NAME" \
  --region us-east-2 \
  --query "VpnConnections[0].VgwTelemetry[*].[OutsideIpAddress,Status.TunnelStatus]" \
  --output table'

# Expected: Tunnel 1 returns to UP, BGP re-learns routes

# Peer: Ping should continue normally, then show re-established

Go/No-Go Gate 6.1: Failover Successful

Success Criteria:

Acceptable Disruption: Up to 90 seconds total impact (DPD + BGP reconvergence)

If Gate Fails: One tunnel DOWN causes total loss or slow recovery

See Remediation Playbooks → “Failover Not Working”

Gate 6.1 Passed (or deferred): Redundancy verified or scheduled; proceed to Phase 7

Remediation Playbooks

Playbook 1: Tunnel Stays DOWN

Symptoms: Both tunnels show DOWN in AWS console 30+ seconds after peer initiates config

Investigation:

  1. Verify peer initiated:

    - Peer confirms: Device configuration committed/applied
- Peer confirms: Tunnel/VPN service enabled on device
- Peer confirms: No error messages in device logs

  2. Check network reachability:

    # From peer network (check both endpoints):
nc -uz -w 3 52.14.123.45 500 && echo "UDP 500 reachable" || echo "Unreachable"
nc -uz -w 3 52.14.123.45 4500 && echo "UDP 4500 reachable" || echo "Unreachable"
nc -uz -w 3 52.14.123.46 500 && echo "UDP 500 reachable" || echo "Unreachable"

    If unreachable: Peer firewall is blocking. Add outbound rules for UDP 500, 4500 to tunnel endpoints.

  3. Verify PSK exactness:

    Peer confirms: PSK matches character-for-character from handoff package
Peer checks: No extra spaces, correct case, no typos

    If mismatched: Update PSK in device config and retry tunnel initiation.

  4. Check encryption settings:

    • Phase 1 Encryption: AES-256
    • Phase 1 Integrity: SHA2-256
    • Phase 1 DH Group: DH Group 14 (modp4096)
    • Phase 2 Encryption: AES-256
    • Phase 2 Integrity: SHA2-256

    If mismatched: Update to match standard (see peer-guides), save, and retry.

  5. Check MTU on tunnel path:

    # From peer to AWS endpoint:
ping -c 1 -M do -s 1400 52.14.123.45
# If fails: path MTU < 1472; adjust device to 1350 or use fragmentation

  6. Last resort: Full trace:

    # On peer device, enable IPSec debug:
# [Device-specific: see troubleshooting in peer guide]
# Attempt tunnel initiation
# Capture packets with tcpdump
# Review IKE packets; identify where negotiation breaks

Resolution: - [ ] PSK matches - [ ] Encryption settings standard - [ ] Network reachability confirmed - [ ] Device config committed - [ ] Retry tunnel initiation - [ ] Both tunnels show UP after 10 seconds

Playbook 2: BGP Routes Not Appearing

Symptoms: Tunnels UP but TGW route table shows no peer CIDRs; peer device shows no learned routes

Investigation:

  1. Verify tunnel is actually UP:

    aws ec2 describe-vpn-connections \
  --filters "Name=tag:Name,Values=$PEER_NAME" \
  --region us-east-2 \
  --query 'VpnConnections[0].VgwTelemetry[*].Status.TunnelStatus' \
  --output text
# Must show: UP UP (not DOWN)

    If DOWN: Resolve tunnel issue first (Playbook 1)

  2. Check BGP neighbor configuration:

    Peer confirms: BGP neighbor IPs = 169.254.X.1 and 169.254.Y.1 (inside tunnel IPs)
Peer confirms: BGP neighbor AS = 64512
Peer confirms: Local AS = [peer's assigned ASN]

    If mismatched: Correct BGP config and save

  3. Check BGP neighbor state on peer device:

    Device-specific command (see Phase 4):
- Checkpoint: netstat -rn | grep 169.254
- Fortigate: get router bgp summary
- Palo Alto: show routing bgp peers
- Cisco: show bgp summary

    If shows “Down” or “Idle”: BGP not established despite tunnel UP

  4. Verify BGP hold timers:

    Peer confirms: Hold time ≥ 180 seconds
Peer confirms: Keep-alive ≤ 60 seconds

    If not: Update BGP timers (may speed convergence)

  5. Check route advertisement:

    Peer confirms: Local routes (172.16.0.0/16, etc.) are advertised
Affinity confirms: TGW expects to receive these CIDRs

    If not advertised: Enable route redistribution in BGP (device-specific)

  6. Affinity-side: Check TGW route table acceptance:

    aws ec2 describe-transit-gateway-routes \
  --transit-gateway-route-table-id tgw-rtb-079e9cb450e5355e6 \
  --region us-east-2 \
  --query 'Routes[*].[DestinationCidrBlock,State]' \
  --output table | grep -i "172.16\|blackhole"
# Routes may show as "blackholed" initially if VPN not yet accepting

Resolution: - [ ] Tunnels are UP (both) - [ ] BGP neighbors configured with correct IPs/ASNs - [ ] Peer confirms local routes advertised - [ ] BGP neighbors show as Established - [ ] Routes appear in Affinity TGW table as “active” - [ ] Wait up to 5 minutes for BGP convergence

Playbook 3: Traffic Not Passing

Symptoms: Tunnels UP, routes learned, but ping fails or traffic is dropped

Investigation:

  1. Verify routing on Affinity side:

    # EKS pod attempts to reach peer network:
kubectl exec -it <pod> -- ip route show default
# Should show: default via [VPC gateway IP] dev eth0

# Check TGW route table includes peer CIDR:
aws ec2 describe-transit-gateway-routes \
  --transit-gateway-route-table-id tgw-rtb-079e9cb450e5355e6 \
  --region us-east-2 \
  --query "Routes[?contains(DestinationCidrBlock, '172.16')]" \
  --output table

    If route missing: BGP has not yet propagated; wait and retry

  2. Verify routing on peer side:

    netstat -rn | grep 10.0
# Should show: 10.0.0.0/16 via [tunnel inside IP] dev [tunnel device]

    If missing: BGP has not yet propagated; wait and retry

  3. Check security policies/ACLs:

    Checkpoint:

    Verify: Access rule exists allowing source 10.0.0.0/16 to destination 172.16.0.0/16
Verify: Rule includes VPN community for tunnel
Verify: Rule enabled (not disabled)

    Fortigate:

    Verify: Security policy exists for VPN traffic
Verify: Policy allows bidirectional traffic
Verify: Policy enabled (not grayed out)

    Palo Alto:

    Verify: Security policy allows 10.0.0.0/16 → 172.16.0.0/16
Verify: Policy includes tunnel zones
Verify: Application/service allows traffic

    Cisco:

    Verify: Crypto ACL allows interesting traffic
Verify: Access-list permits source → destination
Verify: Crypto map references ACL

  4. Check NAT:

    Peer confirms: No NAT masking the source IP
Peer confirms: NAT exemption configured (if applicable)
Affinity confirms: Traffic arriving with correct source IP (not NATed)

    If NATed: Disable NAT for tunnel traffic or peer will not recognize return traffic

  5. Test with tcpdump (if available):

    # On Affinity EKS pod:
tcpdump -i any "dst 172.16.1.100"
# [Attempt ping]
# Should show ICMP echo-request going out

# On peer network:
tcpdump -i eth0 "src 10.0.1.0/24"
# Should show ICMP echo-request arriving

  6. Check MTU (may cause silent failures):

    # Packet size test (from Affinity):
ping -c 3 -M do -s 1400 172.16.1.100
# If fails: MTU issue

ping -c 3 -M do -s 1350 172.16.1.100
# If succeeds: Configure path MTU to 1350

Resolution: - [ ] Routes present in both TGW and peer routing tables - [ ] Security policies/ACLs allow traffic bidirectionally - [ ] NAT disabled for tunnel traffic - [ ] MTU sufficient (≥1350 bytes) - [ ] Ping from Affinity EKS pod succeeds with 0% loss - [ ] Peer confirms traffic arriving

Key Technical Insights

1. AWS VPN is Always Responder-Only

Why: AWS Transit Gateway VPN cannot initiate IKE. It only responds to incoming IKE_SA_INIT packets.

Implication: Peer device MUST initiate tunnel. This is not configurable. If peer forgets to enable VPN, tunnels will never come UP.

How to confirm peer initiated: Tunnel status changes from DOWN to UP within 5-30 seconds of peer starting VPN.

2. No BGP State Observable from AWS API

Why: AWS describe-vpn-connections does not expose BGP neighbor state or established/down status.

Workaround: AWS returns StatusMessage like “4 BGP ROUTES” which indicates BGP is working (routes are being received). But we cannot see neighbor state from AWS side.

Implication: Always verify BGP from peer device CLI to confirm actual neighbor establishment.

3. DPD Timeout Varies by Device

Device-specific DPD timeout (how long before detecting a dead peer):

Device DPD Action Default Timeout Failover Time
Checkpoint restart 30s 30s + BGP (~60s total)
Fortigate restart 10s 10s + BGP (~40s total)
Palo Alto clear 10s 10s + BGP (~40s total)
Cisco restart 10s 10s + BGP (~40s total)

Implication: Checkpoint has slower failover (up to 90s). Fortigate/Palo/Cisco faster (~40s).

4. MTU is a Known IPSec Issue

IPSec adds ~50-70 bytes of overhead: - IKEv2 header: ~50 bytes - ESP header + padding + ICV: ~20-40 bytes

Standard Ethernet MTU = 1500 bytes. With IPSec: - Recommended minimum inside MTU = 1350-1370 bytes - AWS recommends maximum payload = 1394 bytes

How to test: Use ping -M do -s 1350 to verify 1350-byte payload succeeds.

5. Both Tunnels are Active-Active

AWS VPN tunnels are NOT active-standby (primary/secondary). Both tunnels are active and carry traffic based on routing (often equal-cost multipath if both routes advertised).

Implication: - If one tunnel fails, remaining tunnel carries all traffic (no switchover needed) - BGP reconvergence determines which tunnel is preferred - Both tunnels contribute to redundancy; losing one does NOT mean service is degraded

6. BGP Convergence Time

After tunnel goes DOWN, BGP takes time to converge:

  1. DPD detects neighbor down: 10-30 seconds (device-dependent)
  2. BGP neighbor state change: ~3 seconds after DPD
  3. Route withdrawal and re-learning: ~5-10 seconds
  4. Total failover time: 15-40 seconds (Fortigate/Palo/Cisco) or 30-90 seconds (Checkpoint)

For SLAs: Plan for up to 120 seconds of potential disruption during single-tunnel failure.
