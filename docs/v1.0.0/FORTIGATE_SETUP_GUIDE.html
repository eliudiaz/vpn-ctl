🎯 Overview

This guide provides step-by-step instructions for configuring a Fortinet FortiGate firewall to establish a secure, redundant VPN tunnel connection to Affinity’s AWS Transit Gateway infrastructure.

What You’re Building

Your Network              Affinity Transit Gateway      AWS Network
(172.16.0.0/16)          (Hub & Spoke)                 (VPCs)
      │                         │                           │
      ├─ Tunnel 1 (Primary)────►│                           │
      │  (52.14.x.x:500)        ├─ Route Propagation ─────►│
      │                         │                           │
      ├─ Tunnel 2 (Secondary)──►│                           │
      │  (52.14.y.y:500)        │                           │
      │                         │                           │
      └─ BGP 65000             └─ BGP 64512 (AWS)          │
         (Dynamic Routing)       (Dynamic Routing)         │

Key Benefits

  • ✅ Redundancy: Dual tunnels with automatic failover
  • ✅ Dynamic Routing: BGP learns routes automatically
  • ✅ Encryption: IKEv2 with AES-256, SHA2-256
  • ✅ Low Latency: Direct AWS connectivity
  • ✅ AWS Managed: Transit Gateway handles complexity

Estimated Setup Time: 30-45 minutes

🔐 Tunnel Parameters

Encryption & Authentication Standards

All FortiGate configurations use these identical parameters:

Parameter Value
IKE Version IKEv2
Phase 1 Encryption AES-256
Phase 1 Integrity SHA2-256
Phase 1 DH Group DH Group 14 (modp4096)
Phase 1 Lifetime 28800 seconds (8 hours)
Phase 2 Encryption AES-256
Phase 2 Integrity SHA2-256
Phase 2 PFS Optional (Recommended)
Phase 2 Lifetime 3600 seconds (1 hour)
DPD Timeout 10 seconds
DPD Action restart

Why These Settings?

  • IKEv2: Modern, more resilient than IKEv1
  • AES-256: FIPS 140-2 approved, strong encryption
  • SHA2-256: Industry standard integrity checking
  • DH Group 14: Balances security and performance
  • DPD: Detects and recovers from tunnel failures automatically

🔧 Step-by-Step Configuration

STEP 1: Open FortiGate Web Dashboard

  1. Navigate to https://[fortigate-ip]:443 or use FortiManager
  2. Log in with admin credentials
  3. Navigate to VPN → IPSec Tunnels

STEP 2: Create IPSec Phase 1 Configuration

  1. Click Create New
  2. Configure Phase 1 (IKE):
    • Name: Affinity-ATG-Tunnel-1 (for first tunnel)
    • Remote Gateway: 52.14.X.X (Affinity endpoint)
    • Type: Site-to-Site
    • Authentication Method: Pre-shared key
    • Pre-shared Key: [PSK provided by Affinity] (case-sensitive!)
  3. IKE Version Settings:
    • IKE Version: IKEv2 only
    • Encryption: AES-256
    • Authentication (Integrity): SHA2-256
    • DH Group: 14 (modp4096)
    • Lifetime: 28800 seconds
    • Dead Peer Detection: Enable
    • DPD Timeout: 10 seconds
    • DPD Behavior: Restart
  4. Click Create

STEP 3: Create IPSec Phase 2 Configuration

  1. In the same tunnel, go to Phase 2 Selectors tab

  2. Click Create New

  3. Configure Phase 2 (IPSec):

    • Name: Affinity-ATG-Tunnel-1-Phase2
    • Encryption: AES-256
    • Authentication: SHA2-256
    • Enable PFS: Yes (Recommended)
    • DH Group: 14
    • Lifetime: 3600 seconds
    • Autokey (IKE): Enable

  4. Traffic Selectors:

    • Local Address: Your CIDR block (e.g., 172.16.0.0/16)
    • Remote Address: Affinity CIDR block (e.g., 10.0.0.0/16)

  5. Click OK

  6. Repeat Steps 2-3 for Tunnel 2 with:

    • Name: Affinity-ATG-Tunnel-2
    • Endpoint: 52.14.Y.Y
    • PSK: [Second PSK from Affinity]
    • Inside tunnel IPs will be configured after Phase 1 creation

STEP 4: Configure Tunnel Interface IPs

  1. Navigate to Network → Interfaces
  2. For each tunnel, create a new interface:
    • Name: Affinity-Tunnel-1
    • Type: IPSec Tunnel
    • IP/Netmask: 169.254.X.2/30 (your side of tunnel 1)
    • Interface: Select the Phase 1 configuration Affinity-ATG-Tunnel-1
  3. Repeat for Tunnel 2:
    • Name: Affinity-Tunnel-2
    • IP/Netmask: 169.254.Y.2/30 (your side of tunnel 2)
    • Interface: Affinity-ATG-Tunnel-2
  4. Click OK for each

STEP 5: Create Firewall Policy for VPN Traffic

  1. Navigate to Policy & Objects → Firewall Policy

  2. Create new policy:

    • Name: VPN-to-Affinity
    • Incoming Interface: Your LAN interface
    • Outgoing Interface: Affinity-Tunnel-1
    • Source: Your network object (e.g., Local-Network)
    • Destination: Affinity network object (e.g., Affinity-Network)
    • Service: Any
    • Action: ACCEPT

  3. Advanced Options:

    • Enable Logging: On
    • Log Allowed Traffic: On

  4. Click OK

  5. Repeat for Tunnel 2 with:

    • Outgoing Interface: Affinity-Tunnel-2

STEP 6: Configure Static Routes (If Not Using BGP Initially)

  1. Navigate to Network → Static Routes
  2. Add route for Affinity network:
    • Destination: 10.0.0.0/16 (Affinity CIDR)
    • Gateway: 169.254.X.1 (Tunnel 1 gateway - AWS side)
    • Interface: Affinity-Tunnel-1
    • Distance: 20
  3. Add failover route:
    • Destination: 10.0.0.0/16
    • Gateway: 169.254.Y.1 (Tunnel 2 gateway)
    • Interface: Affinity-Tunnel-2
    • Distance: 30 (higher = lower priority)
  4. Click OK

STEP 7: Publish Configuration

  1. Navigate to Dashboard
  2. Click Apply & Close or Save Configuration
  3. Wait for configuration to sync (typically 2-5 minutes)
  4. Verify in syslog: IPSec tunnel is UP

🔄 BGP Dynamic Routing

Step 1: Enable BGP

  1. Navigate to Router → BGP
  2. Enable BGP:
    • Enable BGP: Yes
    • Local AS Number: Your assigned ASN (e.g., 65000)
    • Router ID: Your firewall’s IP address

Step 2: Configure BGP Neighbors

  1. Under Neighbors, click Create New
  2. Configure for Tunnel 1:
    • IP Address: 169.254.X.1 (AWS side of tunnel 1)
    • Remote AS: 64512 (AWS ASN)
    • Timers - Keep Alive: 60 seconds
    • Timers - Hold Time: 180 seconds
  3. Repeat for Tunnel 2:
    • IP Address: 169.254.Y.1 (AWS side of tunnel 2)
    • Remote AS: 64512
    • Timers - Keep Alive: 60 seconds
    • Timers - Hold Time: 180 seconds

Step 3: Configure Route Distribution

  1. Under Route Maps, create:
    • Name: Affinity-Inbound
    • Action: Permit
    • Match: All (accept all routes from AWS)
  2. Under Route Aggregation (optional):
    • Configure to advertise your CIDR blocks to AWS

Step 4: Apply BGP Configuration

  1. Click OK to save
  2. Verify neighbor status shows as “Established”

✅ Verification Procedures

Verify Tunnel Status

In Web Dashboard:

  1. Navigate to VPN → IPSec Tunnels

  2. Check status:

    Affinity-ATG-Tunnel-1: ✓ UP
Affinity-ATG-Tunnel-2: ✓ UP

Via Command Line (SSH):

get vpn ipsec tunnel name Affinity-ATG-Tunnel-1
# Look for: status: up

# Check all tunnels
diagnose vpn tunnel list

Verify BGP Routes

In Web Dashboard:

  1. Navigate to Router → BGP

  2. Check Neighbor Status:

    169.254.X.1: Established
169.254.Y.1: Established

  3. Check Routes Learned:

    10.0.0.0/16 via 169.254.X.1 (BGP)
10.1.0.0/16 via 169.254.Y.1 (BGP)

Via Command Line:

get router bgp neighbors
# Should show: State = Established

get router bgp summary
# Shows routes learned

diagnose firewall route list | grep 10.0
# Routes to Affinity should appear

Test Connectivity

From FortiGate:

execute ping-options source 172.16.0.1
execute ping 10.0.0.10
# Should receive responses without packet loss

From Affinity Side:

Affinity DevOps will verify: - Tunnel endpoints reachable - BGP routes learned - Traffic passing through

🐛 Troubleshooting

Issue: Tunnel Stays DOWN

Symptoms: Both tunnels show DOWN in dashboard

Diagnosis:

diagnose vpn ipsec tunnel list
# Check tunnel state

get vpn ipsec tunnel name Affinity-ATG-Tunnel-1
# Look for error messages

diagnose debug application ike -1
# Enable IKE debugging

Solutions:

  1. Verify PSK Match:
    • Check PSK in FortiGate matches exactly what Affinity provided
    • PSKs are case-sensitive
    • No extra spaces or characters
  2. Check Firewall Rules:
    • Ensure outbound UDP 500, 4500 allowed
    • Check antivirus/IPS not blocking IPSec
  3. Verify Encryption Settings:
    • Confirm IKEv2, AES-256, SHA2-256 selected
    • Check DH Group 14 enabled
    • Verify Phase 1/2 lifetimes match specification
  4. Check Interface IP:
    • Verify tunnel interface IPs configured: 169.254.X.2/30
    • Confirm AWS endpoint IP correct

Issue: BGP Routes Not Learning

Symptoms: Tunnel UP but no routes appearing in routing table

Diagnosis:

get router bgp summary
# Check neighbor count and routes received

diagnose ip route list | grep 10.0
# Should show routes via tunnel

diagnose router bgp summary
# Detailed BGP status

Solutions:

  1. Verify BGP Enabled:
    • Confirm BGP enabled on firewall
    • Check BGP AS number configured
  2. Check Neighbor Configuration:
    • Verify neighbor IP (inside tunnel IP)
    • Confirm AS number 64512 for AWS
    • Check neighbor state = “Established”
  3. Review BGP Timers:
    • Keep alive should be ≤ 60 seconds
    • Hold time should be ≥ 180 seconds

Issue: Traffic Not Passing

Symptoms: Tunnel UP, routes learned, but no data flow

Diagnosis:

diagnose firewall iproutecheck 172.16.0.1 10.0.0.10
# Check if route exists

diagnose sniffer packet any "host 10.0.0.10" 4
# Capture traffic on tunnel

get firewall policy | grep VPN
# Check policy for VPN traffic

Solutions:

  1. Verify Firewall Policy:
    • Confirm policy allows traffic source → destination
    • Check policy outgoing interface matches tunnel
    • Verify policy is enabled and before deny rules
  2. Check Route Priority:
    • Ensure static route distance values correct
    • BGP routes should have lower distance than static
  3. Enable Logging:
    • Log all VPN traffic temporarily
    • Review logs for accepted/dropped packets

🧪 Joint E2E Testing (Phases 3-7)

After device configuration is complete, both Affinity and your DevOps team conduct structured testing via the master protocol: VPN_E2E_TESTING_PROTOCOL.md

This section covers Fortigate-specific testing procedures for each phase.

Phase 3: IKE/IPSec Tunnel Establishment (Layer 1-2)

Timeline: Immediately after configuration is committed

What happens: Your device initiates IKE; AWS responds; tunnels reach UP state

Your action: Monitor tunnel negotiation

# Real-time tunnel status
diagnose vpn tunnel list

# Expected output (Phase 1 & 2 statuses):
# name=aws-tunnel-1
#  phase1_name=aws-p1
#  phase1_state=ESTABLISHED (after negotiation)
#  phase2_name=aws-p2
#  phase2_state=ESTABLISHED (after negotiation)
#
# name=aws-tunnel-2
#  phase1_name=aws-p1-2
#  phase1_state=ESTABLISHED
#  phase2_name=aws-p2-2
#  phase2_state=ESTABLISHED

# Monitor IKE/IPSec in real-time
diagnose vpn ike gateway list

# Verify transform sets active
diagnose vpn ipsec sa list

Affinity verifies: AWS console shows both tunnels UP (via skill-vpn-connectivity)

Gate 3.1: Both tunnels show ESTABLISHED on both sides

If tunnels stay DOWN after 30 seconds: See Troubleshooting → “Tunnel Stays DOWN”

Phase 4: BGP Route Exchange (Layer 3)

Timeline: 5-15 seconds after tunnels reach UP

What happens: BGP neighbors establish; routes learned automatically

Your action: Monitor BGP neighbor state

# Check BGP neighbors (should show Established)
get router bgp summary

# Expected output:
# Neighbor        V    AS MsgRcvd MsgSent   TblVer  InQ OutQ Up/Down State/PfxRcd
# 169.254.10.1    4 64512     10      10        5    0    0 00:05:10        3
# 169.254.11.1    4 64512     10      10        5    0    0 00:05:10        3

# View routes learned from BGP
get router bgp neighbors 169.254.10.1 received-routes

# Verify routes exist in routing table
show routing bgp summary

Affinity verifies: AWS Transit Gateway route table contains your CIDRs with state=active

Gate 4.1: BGP neighbors Established; routes appear in both TGW table and your routing table

If routes don’t appear: See Remediation Playbooks → “BGP Routes Not Appearing”

Phase 5: Data Plane Traffic Test (Layer 4)

Timeline: After Phase 4 gate passes

What happens: Test actual traffic flow across tunnel

Affinity’s Test (from EKS pod)

# Affinity pings a host on your network
kubectl run vpn-test --rm -it --image=alpine -- sh

# Inside pod:
ping -c 10 [YOUR_TEST_IP]  # e.g., 172.16.1.100
# Expected: 0% packet loss, round-trip time ~45-100ms

# Test MTU
ping -c 3 -M do -s 1400 [YOUR_TEST_IP]  # May fail
ping -c 3 -M do -s 1350 [YOUR_TEST_IP]  # Should succeed

Your Confirmation

On your test host, monitor traffic arrival:

# Monitor incoming traffic from Affinity
diagnose sniffer packet any "src 10.0.0.0/8" 4

# Expected: ICMP echo-request packets arriving from Affinity CIDR

# Verify return path uses tunnel
show routing bgp neighbors 169.254.10.1 advertised-routes

# Confirm tunnel is carrying traffic
diagnose vpn ipsec sa list | grep -E "Tunnel|bytes"

Gate 5.1: Bidirectional ping succeeds with ≤1% loss; MTU 1350+ working

If traffic doesn’t pass: See Remediation Playbooks → “Traffic Not Passing”

Phase 6: Redundancy & Failover Test (Layer 5) — OPTIONAL

Timeline: Can be deferred to maintenance window

What happens: One tunnel is disabled; verify other handles all traffic

Your action: Continuous ping during test

# Start continuous ping to Affinity test IP
execute ping-options
set count 1000
set timeout 1
end
execute ping [AFFINITY_TEST_IP]

# Affinity will disable Tunnel 1 on their side
# Expected ping behavior:
# [Normal] ~1ms latency, 0% loss
# [Tunnel 1 DOWN] Brief interruption (1-3 sec)
# [DPD timeout] 10 second delay (Fortigate default)
# [BGP reconvergence] Another 5-10 seconds
# [Resumed] Ping continues normally through Tunnel 2

# Total disruption: 15-25 seconds

Gate 6.1: Single tunnel failure does not cause total outage

Phase 7: Operational Sign-Off

Timeline: After all Phase 5 (or Phase 6) gates pass

Action: Complete bilateral sign-off checklist in VPN_E2E_TESTING_PROTOCOL.md Phase 7 section

Fortigate Verification Checklist: - [ ] diagnose vpn tunnel list shows both tunnels Phase 1 & 2 ESTABLISHED - [ ] get router bgp summary shows neighbors Established - [ ] get router bgp neighbors 169.254.10.1 received-routes shows learned CIDRs - [ ] Data plane ping succeeds (0% loss) - [ ] Failover test completed (if performed) - [ ] Configuration backed up and documented

Once signed: Tunnel is production-ready

📋 Configuration Checklist

Before declaring configuration complete:

IPSec Tunnel Setup: - [ ] Phase 1 created with IKEv2, AES-256, SHA2-256 - [ ] Phase 2 created with matching encryption - [ ] PSKs entered for both tunnels - [ ] Tunnel interface IPs configured (169.254.x.x/30) - [ ] DPD enabled (10 seconds, restart action)

Firewall Policy: - [ ] Network objects created for local and remote CIDR - [ ] VPN firewall policies created - [ ] Policies allow correct source/destination - [ ] Logging enabled on policies

Routing: - [ ] Static routes configured (if not using BGP initially) - [ ] BGP enabled and configured - [ ] BGP neighbors configured - [ ] Local AS number set

Verification: - [ ] Both tunnels show UP - [ ] BGP neighbors show as Established - [ ] Routes from AWS appearing in routing table - [ ] Ping test to AWS network successful - [ ] Logs show successful tunnel negotiation
